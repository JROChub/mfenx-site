From authenticated bytes to inference

Gate 1.1.0rc1 and organization service 0.4.0rc1 extend the existing system. A receipt, independently configured issuer and approved contract, release authorization and runtime policy must agree before the loader consumes its retained immutable model object. Registration of a receipt does not authorize serving.

The CPU profile onnx-cpu-owned-bytes/v1 and CUDA profile onnx-cuda12-owned-bytes/v1 support self-contained ONNX models up to 64 MiB. They reject external weights, custom operators and unsupported profiles. Runtime library and configuration identities are pinned. The CUDA profile prohibits CPU placement fallback and verifies CUDA-resident outputs. These software profiles trust the operating-system kernel.

Policy epochs, persistent release floors, short leases, per-call authorization and durable audit govern sessions. In-flight native operations may finish after revocation. Retained bundle inventory and sealed Linux objects are tested separately; inventory verification does not authorize sharded inference.

A defined model-evaluation relation

The fixed-model SFCS guest consumes the exact public Optdigits ONNX model and dataset, checks their SHA-256 identities within the virtual machine and evaluates one selected row using ordered, nonfused FP32 operations: 64 inputs, 32 ReLU units and 10 output logits. Its 116-byte journal commits the model, dataset, sample index, predicted class, label and logit digest.

The recorded proof covers sample zero and matches an independently computed reference journal. Proof generation took 18.303 s; PHA verification took 1.367 s and capsule verification 1.619 s. These are individual RTX 4090 workload observations, not throughput estimates. The proof establishes this guest relation; it does not establish GPU kernel execution, all-dataset correctness or general model safety.

Linux policy mfenx/admission-policy/v2 requires protocol verification with a sealed, checksum-pinned verifier and independently approved program, model, dataset and result identities before model parsing. The serving audit retains the proof identity. Fifteen actual CUDA/proof-admission tests passed without skips, errors or failures, including proof-backed inference after pathname replacement.

A separate finite GPU contract evaluated all 1,797 public rows: both CPU and CUDA classified 1,729 correctly, with zero changed decisions and maximum absolute logit difference 7.62939453125e-06 against tolerance 0.0001. This used a temporary test authority and does not amend the original CPU release contract.

Retained evidence: guest source, reference, lockfiles and terms · build identity · PHA with execution receipt · Memory Capsule · public statement and report · guest binary · reference journal · file checksums. These files contain public demonstration commitments; verification still requires an independently approved patched verifier and guest identity.

Install the patched native verifier in a dedicated location, then verify the retained proof and capsule. Approve the complete guest and statement identities independently; a successful generic PHA-core check is insufficient.

Security and identity continuity

Power House input acquisition is bounded before full allocation; JSON depth and duplicate keys are checked without changing existing canonical fingerprints. PHA core validity remains distinct from validation of external proof attachments. Rootprint consistency is supplemented by independently authorized model lineage.

The optional proof backend is migrated to RISC Zero SDK 3.1.0 and replacement verifier roots for GHSA-g6qg-9j8p-7j87. Earlier execution receipts must be regenerated. The registry Power House 0.4.1 proof backend predates this migration; install the patched source revision for SFCS verification. Generic PHA and Rootprint identities and the P-256 Receipt v1 transcript are unchanged.

CKODMK 0.5.3rc1 additionally requires its qualified Torch 2.13.0 runtime before checkpoint decoding. Browser evaluation invalidates dependent admission and download permissions whenever model, contract, dataset or issuer changes; superseded asynchronous results cannot restore approval.

Acceptance at enforcement boundaries

The acceptance record distinguishes observed effects from deployment-specific requirements. No pending row is a passing qualification. Confidential execution requires an actual measured CPU/GPU workload, fresh attestation and an independent scoped key broker. Ordinary GPU availability does not establish those properties.

Operational acceptance

The extended deployment suite passed 269 tests and 143 subtests under CPython 3.13 and checksum-pinned Caddy 2.11.9, with no skips. It exercised the frozen offline installer, actual installed-runtime acceptance, browser-format renewal, online database backup and account, license and payment proxies over loopback HTTP. All 22 original wheel identities were preserved.

Four additional CPU serving tests observed signer rotation, consistent database snapshot recovery with retained policy floors, authority outage and loss of durable state. Successful recovery requires owner-controlled state and readmission. These observations do not establish live payment settlement, customer endpoint deployment, fleet resource enforcement or confidential hardware recovery.
