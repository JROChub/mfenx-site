Security boundary

The rc4 candidate retains the existing software admission path. The producer encrypts an already authenticated model with a fresh AES-256-GCM key and nonce. The distribution contains the ciphertext and versioned descriptor; the key remains a separate provisioning artifact. The loader authenticates the entire encrypted model before passing retained immutable plaintext bytes to the existing ONNX validator and runtime. This path creates no plaintext checkpoint file.

The supported bound remains a self-contained ONNX model of at most 64 MiB. It is not an encrypted sharded-model runtime. Receipt v1 signatures, existing CPU/CUDA profiles and PHA/Rootprint identities retain their meanings. The rc1 downloads and observations remain available unchanged.

Release, key delivery and inference

Authenticated release + exact plaintext identity
    → encrypted artifact + independently approved descriptor
    → measured workload + upstream Trustee protocol
    → scoped recipient-bound key delivery
    → complete AEAD authentication + plaintext identity check
    → existing model/proof/lineage admission
    → retained model loading + authorized serving

MFENX uses the upstream Trustee protocol for fresh evidence, recipient keys and encrypted resource delivery. The constrained client accepts only the approved HTTPS origin and certificate roots, follows no redirects and receives no caller-provided cached token, recipient-key file, proxy setting or administrator credential. Its executable and certificate are copied into sealed Linux memory objects and checked against independent policy pins.

The adapter acquires the returned key through an anonymous memory file, accepts exactly 32 key bytes and applies child memory, CPU, wall-time and output-size limits. Linux parent-death supervision kills the native key client when its admission parent dies; the launcher checks the expected parent after arming that signal. Tests also observe kernel-enforced output-limit termination. It does not log the key. Python and native code may create memory copies; deleting a reference does not establish zeroization. Protected guest memory, swap, dumps and teardown require actual hardware qualification.

Complete policy and measured launch identity

The additive policy mfenx/encrypted-admission-policy/v1 binds the existing admission policy, descriptor digest, broker origin, broker CA and client executable. The entire wrapper digest participates in the existing persistent epoch/floor checks. Changing distribution or broker configuration at the same epoch cannot reopen a durable authority.

The approval tool generates exact-byte TOML launch data in the pinned Trustee v0.22 format. The resource policy requires the selected TDX or SNP CPU evidence class, a NVIDIA GPU submodule, affirming appraisals, explicit trust-vector values, the approved resource and matching measured launch claims. Passing launch data at runtime is insufficient: the actual guest must bind its digest into the attested launch measurement.

Trustee must authenticate attestation-token signer roots and perform vendor verification and reference-value appraisal. The generic upstream sample/default resource policy does not satisfy the MFENX deployment policy. Broker denial stops new key acquisition; revoking already loaded sessions additionally requires serving-policy withdrawal or lease expiry. An already delivered key cannot be retracted from its recipient.

Observed software enforcement

The frozen rc3 wheel passed 96 tests with zero skips, errors or failures. The run included 19 encryption/loader cases and 12 actual local Trustee integration cases, and three native child-process cases, alongside receipt, legacy adapter, CPU admission, recovery and gateway tests. Every installed SDK module matched the frozen wheel. Two source builds produced identical 37,179-byte wheel contents.

The canary policy is diagnostic: it makes no executable-approval assertion and does not authorize model-key resources. It is not the MFENX model-admission policy. The initial native canary used local GPU signature/nonce verification; the final native run used NVIDIA remote firmware appraisal. Parsed local measurements alone are not a firmware appraisal.

The complete confidential model profile remains unqualified. It requires launch-time binding of the exact approved initdata, independently approved guest/workload references, and end-to-end protected model-key loading, revocation and recovery tests. The verifier must retain those requirements rather than accept the stock guest's zero value. A declared manifest digest is not proof that its named workload executed.

The hardware service builder pins its upstream source, Intel DCAP library and headers. Hardware client builds check for the pinned NVIDIA native SDK before compiling. Both service builders configure zero JWT clock-skew allowance and enforce not-before claims. The additional local software suite passed 12 protocol tests, including recently expired and future-validity signed-token rejection.

The temporary VM was released and the API reported no active Pods. Permanent GPU hosting is not required to develop or distribute MFENX; confidential GPU workloads require compatible deployment infrastructure. Release acknowledgment does not independently demonstrate hardware memory zeroization.
